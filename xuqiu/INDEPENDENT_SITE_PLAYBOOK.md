# 独立站建设可复用 Playbook

> [!abstract] 核心问题
> 做下一个独立站时，怎样避免“先做首页、反复改视觉、最后才补 SEO、表单和部署”的返工？怎样把内容、设计、开发、搜索、转化和发布组织成一套可以重复使用的流程？

本文件从 GE Chemical Masterbatch 独立站项目提炼，用于后续其他 B2B、产品型
或内容型独立站。它不依赖具体行业、品牌或 WordPress 主题。

## 1. 核心公式

独立站不是“先做首页，再补产品页”。更稳定的顺序是：

```text
商业目标
→ 客户与搜索意图
→ 页面结构
→ 内容证据
→ 转化路径
→ 视觉系统
→ 技术实现
→ SEO / 统计 / 表单
→ 测试
→ 发布与回滚
→ 内容迭代
```

先定页面要完成什么任务，再决定页面长什么样。

## 2. 项目启动时必须拿到的信息

### 商业信息

- 卖什么，不卖什么；
- 目标客户是谁；
- 客户采购时最关心什么；
- 询盘、购买、预约或下载的目标动作；
- 业务能公开的公司事实；
- 不能公开的事实、客户和参数。

### 产品信息

- 产品线和分类；
- 每个分类的产品范围；
- 具体 SKU、型号或牌号；
- 哪些参数有文件证明；
- 哪些参数必须按项目确认；
- 样品、报价、交期和文件申请流程。

### 运营信息

- 谁接收询盘；
- 谁负责回复；
- 正常响应时间；
- 邮件服务商和收件邮箱；
- GA4 和 Search Console 账号；
- 隐私、Cookie 和数据保留要求；
- 域名、DNS、服务器和证书负责人。

这些信息应在开发前收集。不要等网站上线后再找 GA4、SMTP 或法务负责人。

## 3. 页面结构先做成矩阵

为每个页面建立一行：

| 页面 | URL | 搜索意图 | 主 CTA | 需要的证据 | 内链 | Schema |
|---|---|---|---|---|---|---|
| 首页 | `/` | 品牌与核心品类 | 询盘 | 公司事实、产品范围 | 分类、文章、联系 | WebPage |
| 产品分类 | `/products/...` | 品类比较 | 查看产品 | TDS、应用、牌号 | 产品详情、文档 | CollectionPage |
| 产品详情 | `/products/.../<sku>/` | 具体牌号 | 报价或样品 | 当前 TDS | 分类、相关牌号 | Product |
| 文章 | `/blog/.../` | 教育型搜索 | 相关产品 | 可引用资料 | 产品、FAQ | BlogPosting |
| FAQ | `/faq/` | 异议处理 | 询盘 | 明确政策与边界 | 产品、文档 | FAQPage |

原则：

- 每个页面只承担一个主要任务；
- 一个主 CTA，最多一个辅助 CTA；
- 新页面必须有至少一个“从哪来”和两个“下一步”内链；
- 不创建只有关键词、没有实际内容的空页面；
- 产品分类和产品详情必须是两种页面模型，不能只换标题。

## 4. 内容必须先有证据

页面文案不是从竞品复制。先建立内容证据表：

| 事实 | 来源 | 版本/日期 | 适用范围 | 可否公开 |
|---|---|---|---|---|

规则：

- 单个 SKU 的文件不能证明整个产品线；
- 样品报告不能扩展成全系列认证；
- 典型值、规格值和客户验收值必须区分；
- 无法证明的参数写“按具体项目确认”，不补通用数字；
- 公司事实和数据必须由业务方确认；
- 技术文件采用申请和审核流程时，不能暗示公开下载。

可复用的内容结构：

- 页面摘要：这个页面解决什么问题；
- 适用范围：覆盖什么；
- 核心事实：已知信息；
- 选择依据：客户需要准备什么；
- 流程：之后发生什么；
- 边界：哪些内容仍需按项目确认；
- CTA：下一步做什么。

## 5. 设计先做系统，再做页面

### 固定设计系统

- 2 个字体族以内；
- 5–8 个核心颜色；
- 一套间距；
- 一套圆角；
- 一套按钮；
- 一套表单；
- 一套响应式断点。

先写 `DESIGN.md` 和 Design Tokens，再开始页面。

### 评审流程

1. 页面目标与内容结构；
2. 桌面和手机草图；
3. 静态高保真预览；
4. 当前/新版对照；
5. 用户确认；
6. 进入生产模板。

不要在未确认内容结构时连续做多版视觉，否则通常只是反复换布局。

### 产品页原则

- Hero 展示产品，而不是抽象装饰；
- 每个区块回答不同问题；
- 参数、应用、包装、文件和 CTA 不能重复表达；
- 图片必须与文案对应；
- 卡片和表格只承载适合卡片和表格的信息；
- 手机端必须单独设计阅读顺序。

## 6. 技术架构尽量把内容和展示分开

推荐模式：

```text
内容源
→ CMS 页面/文章
→ 页面模板
→ 组件
→ 全局设计系统
```

WordPress 项目可采用：

- Markdown/结构化内容包作为内容源；
- Gutenberg 或自定义字段保存正文；
- 子主题保存模板和组件；
- 页面专属 CSS 按模板加载；
- MU Plugin 处理导入、表单和跨页面 SEO，而不是把业务逻辑写进模板。

对其他技术栈同样成立：

- Next.js/Astro：内容与路由分开；
- Shopify：产品数据、模板和 section schema 分开；
- Webflow/Framer：CMS collection 与页面模板分开。

不要把所有内容硬编码进一个首页文件。否则后续每篇文章和产品都要重新开发。

## 7. URL 和模板必须提前规划

推荐：

```text
/
/products/
/products/category/
/products/category/product/
/blog/
/blog/article-slug/
/resources/tool-or-checklist/
/about/
/contact/
```

规则：

- 产品最多 3–4 层；
- URL 只使用英文、小写和连字符；
- 分类页和详情页分别设置模板；
- 页面改名时同步设置 301；
- 旧页面删除前先确认没有搜索流量和内链；
- 不创建重复 slug 或占位页。

## 8. SEO 在新站阶段就要做

每个页面上线前必须确定：

- 主关键词；
- 搜索意图；
- Title；
- Meta Description；
- Canonical；
- H1；
- H2/H3；
- 内链；
- 图片 Alt；
- Schema；
- 是否应被索引。

建议：

- 首页承接品牌和核心品类；
- 分类页承接品类词；
- 产品页承接型号或具体需求；
- 文章承接教育型、问题型和采购型搜索；
- 应用页承接“品类 + 工艺或用途”关键词。

不要把 Sitemap 提交等同于收录。至少要区分：

1. 页面已发布；
2. Sitemap 包含 URL；
3. Google 已抓取；
4. 页面已进入索引；
5. 页面开始产生搜索展现和点击。

## 9. 图片从第一天就按 SEO 资产处理

- 使用 WebP 或 AVIF；
- 保留有意义的文件名；
- 写实际描述画面的 Alt；
- Hero 设置高优先级，首屏以下图片懒加载；
- 有明确宽高；
- 不重复使用同一张图填满所有页面；
- 产品、工厂、包装和流程图片分别管理。

如果图片放在主题或静态目录，而不是 CMS 媒体库，要显式补录图片 Sitemap。

## 10. 转化路径必须是一条真正的闭环

表单至少包含：

- 明确的价值说明；
- 必要字段；
- 可见标签；
- 服务端验证；
- 防垃圾机制；
- 隐私同意；
- 成功和失败状态；
- 保存记录；
- 邮件通知；
- 失败兜底。

发布前用真实邮箱做测试。收到记录不算完成，邮件实际到达才算完成。

可复用事件：

```text
quote_submit_success
quote_submit_error
document_request_success
document_request_error
sample_request_success
contact_submit_success
```

事件不发送姓名、邮箱、电话、公司或表单正文。

## 11. 统计和搜索账号应在开发阶段准备

开发前索要：

- GA4 Measurement ID；
- GA4 API Secret（如使用 Measurement Protocol）；
- Search Console 权限；
- 网站验证文件或 DNS 权限；
- 广告平台 Pixel（如有）；
- CRM 或邮件平台账号（如有）。

上线门禁：

- GA4 代码只加载一次；
- 页面浏览可见；
- 关键事件已触发；
- 数据已进入 GA4；
- Key Event 已设置；
- GSC 已验证；
- Sitemap 已提交；
- 抽查 URL Inspection；
- 404、301 和 noindex 状态正确。

## 12. 测试体系比单次人工检查更可靠

至少覆盖：

- 桌面 1440px；
- 平板 768px；
- 手机 390px；
- 窄手机 320px；
- 页面宽度没有横向溢出；
- Header/Footer；
- 菜单；
- 表单；
- 路由；
- Title、Description、Canonical；
- Schema、Open Graph；
- Sitemap、robots；
- 图片加载；
- 404 和 301；
- CMS 正文与页面输出一致。

推荐 Playwright 用例：

```text
homepage.spec
product-category.spec
product-detail.spec
article.spec
contact-form.spec
privacy.spec
seo-audit.spec
sitemap.spec
mobile-overflow.spec
```

## 13. 发布必须是版本化流程

推荐结构：

```text
/var/www/site/
├── current -> releases/20261116-1
├── releases/
│   └── 20261116-1/
└── shared/
```

流程：

1. 复制当前干净 release；
2. 只应用本次变更；
3. 运行语法、构建和测试；
4. 原子切换 symlink；
5. 重载 PHP/应用进程；
6. 清理 cache；
7. 验证正式域名；
8. 保留上一版回滚。

不要直接覆盖生产目录。不要只看文件上传成功就认为发布完成。

## 14. 每次发布写清四件事

- 改了什么；
- 怎么验证；
- 有哪些风险；
- 如何回滚。

发布历史单独保存，不要写进项目规则文件。

推荐文档结构：

```text
AGENTS.md                  # 稳定规则
SITE_RELEASE.md            # 发布检查
DESIGN.md                  # 设计系统
DEPLOYMENT_LOG.md          # 日期化历史
PROJECT_FACTS.md           # 已确认的公司和产品事实
```

## 15. 后续项目直接复用的最小模板

### 页面 Brief

```text
页面名称：
URL：
目标客户：
搜索意图：
主关键词：
主要任务：
主 CTA：
需要的证据：
内链入口：
内链出口：
Schema：
是否索引：
```

### 上线 Definition of Done

```text
[ ] 内容和来源已确认
[ ] 桌面/手机已完成
[ ] SEO 字段完整
[ ] Schema 和 Open Graph 正确
[ ] Sitemap 和 robots 正确
[ ] 表单和邮件实际可用
[ ] GA4 和 GSC 已验证
[ ] 没有横向溢出或坏图
[ ] 有回滚版本
[ ] 发布记录已更新
```

## 16. 这次项目最值得复制的做法

### 应该复制

- 先内容、后设计；
- 页面结构矩阵；
- 统一 Design Tokens；
- 分类页和详情页分开建模；
- 内容和模板分离；
- 产品事实与合规边界；
- Playwright 桌面/手机回归；
- 图片 Sitemap；
- release 目录与回滚；
- Search Console、GA4、SMTP 上线门禁；
- 规则、设计、发布和历史文档分开。

### 不应复制

- 先做多个视觉效果再找内容；
- 把所有页面硬编码进首页；
- 用主题图片却不补图片 Sitemap；
- 公开页面发布后仍用旧 Markdown 直接覆盖；
- 把代码接入当成 GA4、GSC 或邮件已完成；
- 直接在 `current` 目录改生产文件；
- 不保留上一版 release；
- 把长期发布历史全部塞进 `AGENTS.md`；
- 在未完成业务账号、SMTP、法务和备份前宣称网站完整上线。

## 17. 推荐的新项目执行顺序

```text
第 1 周：业务、客户、页面矩阵、关键词、事实清单
第 2 周：内容结构、产品分类、CTA、表单需求
第 3 周：Design System、首页与核心模板草图
第 4 周：产品页、文章模板、响应式设计
第 5 周：CMS、模板、表单、SEO、Schema
第 6 周：Playwright、图片、Sitemap、GA4、GSC、SMTP
第 7 周：内容补齐、法务、备份、预发布验收
第 8 周：正式发布、监控、索引和转化优化
```

周期可以压缩，但顺序不应反转。

## 18. 最终判断标准

一个独立站是否真正完成，不看首页是否漂亮，而看：

- 客户能否快速理解你卖什么；
- 搜索意图与页面结构是否匹配；
- 产品事实是否有证据；
- 主要 CTA 是否可用；
- 询盘是否可靠到达；
- 搜索和统计是否可衡量；
- 手机端是否可用；
- 发布后能否恢复；
- 新内容能否持续扩展。

满足这些条件后，独立站才是可持续运营的资产，而不是一次性设计稿。
